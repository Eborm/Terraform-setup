# Cluster Operations

## Working directories

The repository has two independent Terraform roots.

| Root | Working directory |
|---|---|
| Infrastructure | `Infrastructure/` |
| Cluster | `Cluster/` |

Always run Terraform from the root being changed.

## Kubeconfig convention

The kubeconfig generated by Talos is:

`Infrastructure/kubeconfig`

When working inside the `Cluster` directory, all kubectl commands
must explicitly use:

`KUBECONFIG=../Infrastructure/kubeconfig`

Example:

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get nodes
```

Do not rely on the host's default kubeconfig.

This is the standard command convention for this project.

## Common Kubernetes commands

Run from the `Cluster` directory.

### Cluster nodes

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get nodes -o wide
```

### Namespaces

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get namespaces
```

### All pods

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get pods -A -o wide
```

### Ingress resources

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get ingress -A
```

### Services

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get svc -A
```

### Persistent volumes

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get pv
```

### Persistent volume claims

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get pvc -A
```

### Storage classes

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get storageclass
```

### Recent events

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl get events -A --sort-by=.metadata.creationTimestamp
```

### Pod logs

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl -n ntfy logs deployment/ntfy --tail=100
```

### Describe a pod

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl -n ntfy describe pods -l app.kubernetes.io/name=ntfy
```

## Common Terraform workflow

Run inside `Cluster/`:

```bash
terraform fmt -recursive
terraform validate
terraform plan
```

Review the complete plan.

Apply only after verifying the planned changes:

```bash
terraform apply
```

Do not use Terraform apply as a substitute for checking application
health.

After an apply, check the affected Kubernetes resources and logs.

## Terraform refresh and state

Terraform refreshes managed resource state during plan.

Do not manually edit Terraform state unless there is a specific,
understood recovery procedure.

Do not copy state files between the Infrastructure and Cluster
roots.

Protect state files because they may contain sensitive values.

## Alertmanager API access

Alertmanager is internal-only and exposed through a ClusterIP
service on port 9093.

Create a local port-forward:

```bash
KUBECONFIG=../Infrastructure/kubeconfig kubectl -n monitoring port-forward svc/alertmanager-main 19093:9093
```

In another terminal:

```bash
curl -fsS http://127.0.0.1:19093/api/v2/status
```

Check receivers:

```bash
curl -fsS http://127.0.0.1:19093/api/v2/receivers
```

Check active alerts:

```bash
curl -fsS http://127.0.0.1:19093/api/v2/alerts
```

Stop the port-forward with Ctrl+C when finished.

## Release and configuration changes

For each component upgrade:

1. Inspect the existing Terraform version pin.
2. Read the upstream release notes.
3. Check chart values and breaking changes.
4. Update one component at a time.
5. Run terraform fmt.
6. Run terraform validate.
7. Review terraform plan.
8. Apply.
9. Verify pods, services, endpoints and logs.
10. Update the inventory documentation.

## Git workflow

Before staging changes:

```bash
git status --short
git diff --check
```

Stage only the intended files.

Review staged changes:

```bash
git diff --cached --check
git diff --cached --stat
git diff --cached
```

After committing:

```bash
git status
git log -1 --oneline
```

Never stage secrets.auto.tfvars, kubeconfig or Terraform state.
